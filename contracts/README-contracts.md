# Контракт DraftProject 1.0.0

`project.schema.json` — JSON Schema Draft 2020-12 для авторского проекта. Это **входной план**, а не готовый таймлайн. Файл `examples/novostroykin/project.json` проходит структурную проверку, но требует подготовленного каталога, привязки голосов и настоящего скриншота перед финальным рендером.

## Что зафиксировано

- Формат MVP: 1080×1920, 30 fps, русский язык, от одного до двух персонажей, до 12 сцен.
- Желаемая длительность — `target_duration_seconds` в диапазоне 20–45 секунд. Это творческая цель, а не команда ускорить голос. Жёсткий предел финала — 60 секунд / 1800 кадров при 30 fps.
- `seed` управляет процедурными деталями: морганием, микродвижениями и иными разрешёнными вариациями. Он не обещает детерминизм стороннего TTS. Для повторяемого рендера надо фиксировать готовый звук, alignment, хеши ассетов, версии renderer и шрифтов.
- Версии стиля, персонажей и ассетов имеют вид `major.minor.patch`. Все ссылки должны разрешаться в неизменяемую зарегистрированную версию; `latest` запрещён.
- Пресеты подписей, поз, эмоций, жестов и компоновки разрешаются внутри зафиксированной версии стиля/персонажа. Их ID не означают произвольный код.
- Внутри draft нет путей, удалённых URL, ключей, provider voice ID, команд shell или JavaScript. `register_asset` принимает абсолютный локальный путь внутри `TOON_IMPORT_ROOTS`, копирует байты в immutable storage и вычисляет хеш; проект хранит только `asset_id` и `version`.
- `additionalProperties: false` применяется ко всем объектам. Неизвестные поля нужно отклонять с JSON Pointer ошибки, а не молча игнорировать.

## Порядок получения времени: сначала звук

1. Проверить структуру, ссылки, доступные пресеты и ограничения.
2. Для каждой реплики получить TTS либо декодировать зарегистрированную запись.
3. Получить фактическую длительность аудио; при доступности — подтверждённый alignment нормализованных слов. Сопоставить заявленный transcript и metadata с репликой, проверить интервалы. Без подключённого распознавания код не определяет смысловое соответствие речи и текста: речевой fixture проверяется вручную. Не выдавать оценочное распределение слов за точную синхронизацию.
4. Последовательно разместить реплики, паузы и сцены. В MVP диалоги не перекрываются.
5. Разрешить anchors событий/оверлеев и построить compiled timeline.
6. Проверить финальную длительность, положение текста, доступность ассетов и только затем рендерить.

Для `dialogue` сцены длительность в аудиовремени равна `lead_in_ms + сумма(фактическая длительность реплики + pause_after_ms) + tail_ms`. `pause_after_ms` последней реплики тоже учитывается; это не синоним `tail_ms`. Для `hold` сцены длительность задаёт только `hold_ms`; реплики в таком объекте запрещены. Статичный CTA поэтому не зависит от TTS.

При выходе за цель 20–45 секунд проверка выдаёт предупреждение `TARGET_DURATION_MISSED`. При превышении 60 секунд финальный рендер блокируется ошибкой `DURATION_LIMIT_EXCEEDED`. Нельзя автоматически обрезать реплику, ускорять голос или удалять сцену, чтобы уложиться: требуется новая revision сценария.

## Семантика anchors и слов

- `scene_start` / `scene_end` — границы текущей сцены.
- `utterance_start` / `utterance_end` — начало/конец аудио реплики **без** её последующей паузы. Реплика должна находиться в текущей сцене.
- `word_start` / `word_end` — граница нормализованного слова реплики.
- `normalized_word_index` — индекс с нуля в массиве `normalized_words`, который возвращает стадия подготовки аудио. Это не номер элемента, полученного через `text.split(" ")`, и не provider token index.
- Если `offset_ms` отсутствует, компилятор использует 0; JSON Schema `default` сам не изменяет входной документ. Смещение прибавляется после разрешения базовой границы.
- Все вычисленные anchors должны попасть внутрь своей сцены. Событие не переносится молча в соседнюю сцену. Для `events.at` разрешён диапазон `[scene_start, scene_end)`, для конца оверлея — также точная граница `scene_end`.
- У оверлея `end` должен быть строго позже `start`. В hold-сцене доступны только scene anchors; ссылка на реплику там ошибочна.

До синтеза используется единая версионированная нормализация текста: Unicode NFC, нормализация пробелов/кавычек, отделение внешней пунктуации от слов. Русские буквы, `ё` и смысл исходного текста сохраняются. Числа, сокращения и сложные токены должны иметь явное соответствие между отображаемым текстом и spoken words. Нормализатор нельзя менять посреди job; его версия фиксируется в compiled timeline. Окончательный `normalized_words` и связи с исходным текстом должны быть доступны для проверки и исправления anchor. Если TTS вернул символы либо токены другого вида, адаптер преобразует их к этому контракту. Если преобразование неоднозначно, вернуть ошибку alignment, а не угадать индекс.

В примере у `advisor_intro` слова `Я`, `подписался`, `на`, `уведомления`, `в`, `Новостройкине` имеют индексы 0–5. Жест `show_phone` привязан к началу слова `на` (индекс 2). Это демонстрация word anchor; режиссёр может перенести жест на индекс 3 или на начало реплики новой revision.

## Кадры существуют только в compiled timeline

Draft не принимает `start_frame`, `end_frame`, `duration_frames` или абсолютные секунды реплик. После подготовки звука компилятор получает монотонные абсолютные границы и переводит их в целые кадры один раз. Все интервалы timeline имеют вид `[start_frame, end_frame_exclusive)`. Нельзя независимо округлять каждый кусок длительности и накапливать ошибку; соседние интервалы используют одну общую рассчитанную границу.

Рекомендованная фиксированная политика для событий: округление абсолютного времени к ближайшему кадру, midpoint away from zero. Для общей длительности — ceiling фактического конца в кадрах, чтобы не отрезать звук. Аудиодорожка остаётся привязанной к исходным sample positions; кадровый таймлайн определяет визуальные cue. Расхождение визуальной границы с аудио должно укладываться в один кадр. Положительные интервалы, схлопнувшиеся после округления, отклоняются либо расширяются до одного кадра только по явно описанной политике компилятора; молчаливые разные правила в .NET и JS запрещены.

## Состояние сцены и события

- `cast` описывает **видимых** персонажей. Закадровый голос может принадлежать персонажу из project.characters, отсутствующему в текущем cast; так устроена сцена `bot_setup`.
- `camera` и значения cast задают состояние в начале сцены. Оно сбрасывается в начале следующей сцены, если не повторено в её draft.
- `gesture` запускает доверенный жест из каталога персонажа. Длительность/кривая жеста определяются его versioned manifest; по завершении персонаж возвращается к исходной позе. Новый жест того же персонажа прерывает старый.
- `emotion` действует до следующего emotion cue того же персонажа либо конца сцены.
- `camera` меняет план за `transition_ms`. Начало перехода — anchor события; переход обязан закончиться до следующего camera cue и до конца сцены.
- Cue упорядочиваются по разрешённому времени. Два cue одного персонажа и одного канала или два camera cue в один момент — ошибка `AMBIGUOUS_CUE`, а не зависимость от порядка массива.
- Нельзя адресовать жест/эмоцию невидимому персонажу или наводить close_up на отсутствующего в cast персонажа. Закадровый звук не делает персонажа видимым.
- Оверлеи рисуются в порядке массива поверх сцены. Титры/субтитры компонуются в принятой для MVP безопасной зоне `x=80..900`, `y=180..1580` на холсте 1080×1920; это продуктовый пресет, а не обещание универсальных границ Instagram UI. Конфликт важных текстов валидируется после layout. Для scene.kind=hold звук речи отсутствует; project music может продолжаться.

## Точные скриншоты приложения

Image overlay использует `render_mode: exact` и `fit: contain`: зарегистрированное изображение вставляется с сохранением содержимого и пропорций. Допустимы масштабирование и внешняя рамка телефона; запрещены генеративная перерисовка интерфейса, подмена текста, растяжение и crop, скрывающий исходное содержимое. Для скриншотов в manifest сохраняются исходный SHA-256, размеры и media type. Проверка читаемости/безопасной зоны проводится на preview; `exact` не означает битовую идентичность пикселей после масштабирования и видеокодирования.

## TTS и собственная запись

`audio.mode=tts` содержит только `voice_alias` и художественный delivery preset. Worker разрешает alias в настроенный provider/model/voice. Если alias не привязан, вернуть `VOICE_NOT_CONFIGURED`; нельзя молча выбрать случайный голос. Delivery — пожелание к адаптеру, а не гарантия наличия одноимённого параметра у провайдера; неподдерживаемые возможности должны быть явно отражены в validation/capabilities. В MVP каждая реплика синтезируется независимым запросом: без previous_text/next_text, request stitching и других зависимостей от соседних реплик. При неизменных тексте и настройках это сохраняет кеш соседних реплик после локальной правки.

`audio.mode=recording` вместо голосового alias ссылается на зарегистрированный audio asset. Пример замены объекта `audio` одной реплики:

```json
{
  "mode": "recording",
  "asset": { "asset_id": "buyer_problem_recording", "version": "1.0.0" }
}
```

Текст реплики всё равно обязателен: он нужен для сопоставления заявленного transcript, captions и word anchors. Подготовка аудио сообщает несовпадение **заявленных** текстов, непригодный звук и отсутствие alignment там, где он требуется. Она не обещает автоматически распознать смысловое расхождение произнесённой речи и текста без ASR. Mouth movement по амплитуде допускается как обозначенная ограниченная анимация и не заменяет word/phoneme alignment.

## Sidecar для записанной речи

`audio-alignment.schema.json` задаёт WordAlignment 1.0.0. При импорте WAV/MP3 `register_asset` может принять `alignment_path` — абсолютный путь к JSON sidecar внутри той же allowlist `TOON_IMPORT_ROOTS`. Регистратор проверяет схему и интервалы, импортирует immutable копию и связывает хеши sidecar и аудио в metadata audio asset. Draft по-прежнему ссылается только на audio asset; отдельного локального пути в нём нет. Повторный импорт изменённого sidecar требует новой immutable версии asset.

Production sidecar имеет `example_only:false` и `source:manually_verified` либо `provider_alignment`. Первое — заявленная ручная проверка поставщиком разметки, второе — результат провайдера; эти значения не означают, что наш сервер выполнил ASR. `tests/fixtures/recorded-line.alignment.json` — **только иллюстративная разметка с вымышленными временами, без соответствующей аудиозаписи**. Поэтому у него `example_only:true` и нет source. Его можно проверять по схеме, но нельзя регистрировать как готовый production alignment или использовать в финальном рендере. Простое изменение флага не заменяет запись и её проверку.

`transcript_text` описывает произнесённый текст. `normalized_words` содержит непрерывные уникальные индексы `0..N-1`, слова и границы `start_ms/end_ms` от начала аудио. Семантическая проверка требует `0≤start_ms<end_ms≤duration_ms`, `end_ms[i]≤start_ms[i+1]` и соответствия нормализованного transcript списку слов. Паузы между словами допустимы, перекрытия — нет. `duration_ms` сверяется с реальной длительностью декодированного PCM после обработки encoder padding; допустимое расхождение — не более 50 ms. Границы слов также должны попадать в фактическое декодированное аудио; допуск общей duration не разрешает слова за его концом. Эти межполевые проверки выполняет код, не JSON Schema.

Необязательный `display_spans` связывает отображаемый текст с диапазонами `[start_word_index,end_word_index_exclusive)`. Диапазоны идут подряд без дыр и перекрытий и полностью покрывают `0..N`; конкатенация `text` без дополнительного разделителя даёт отображаемую реплику. Так можно явно сопоставить цифру в captions нескольким произнесённым словам. Внутренние пробелы/пунктуация сохраняются в span.text. Без display_spans отображается текст реплики, и его нормализованные слова должны совпадать с transcript. Для span начало берётся из первого слова диапазона, конец — из последнего; неизмеренное время не изобретается.

SRT/посегментная разметка может служить источником фразовых captions, но сама по себе не является word alignment и не удовлетворяет `word_start`/`word_end` anchors.

## Режим субтитров

`captions.mode` обязателен: `auto`, `word` или `utterance`. При `enabled:false` captions не рисуются, но наличие word anchors всё равно требует alignment. При `enabled:true`: `auto` использует word timing, если он проверен, иначе показывает целую реплику на время её звучания; `word` без проверенного alignment даёт `ALIGNMENT_UNAVAILABLE`; `utterance` всегда показывает всю реплику целиком. В word-режиме группировка/подсветка использует только реальные границы слов или display_spans.

Без word/phrase timing нельзя делить длинную речь на равные отрезки ради смены captions. Если целая реплика не помещается в безопасной зоне максимум в две строки при шрифте не меньше 36 px, вернуть `CAPTION_OVERFLOW` и предложить более короткий отображаемый текст с явным mapping, исправление сценария либо подтверждённый alignment. Нельзя молча уменьшать шрифт, обрезать текст или выдумывать тайминг. Word anchors требуют проверенного alignment независимо от captions.mode.

## Что проверяет схема и что проверяет код

JSON Schema проверяет типы, обязательные поля, неизвестные свойства, диапазоны, форму ссылок и взаимоисключающие варианты объектов. Она **не** проверяет существование assets/voices, совпадение SHA-256, уникальность отдельных ID внутри объектов массива, реальную длительность аудио, ссылки между сценами, диапазон word index, хронологию anchors, коллизии событий, совместимость жеста с rig, попадание в safe area или права на media. Это обязательные semantic validation и compile checks приложения.

Обязательные semantic checks: уникальные scene_id/utterance_id/event_id/overlay_id во всём проекте; уникальные character_id в characters и cast; все character/utterance/asset ссылки разрешимы; utterance anchors локальны текущей сцене; word indices попадают в normalized_words; cue не адресуют отсутствующие объекты; computed intervals корректны; финальный output ≤1800 кадров; все media доставлены в immutable render snapshot.

Результат проверки должен различать `schema_valid`, `semantic_valid`, `audio_ready`, `render_ready`, а также включать `errors`, `warnings`, `missing_dependencies`, точные JSON Pointer и, после audio preparation, измеренную длительность. Статус «schema valid» нельзя показывать как «можно рендерить».

## Граница с MCP API

MVP предоставляет `studio_doctor`, `get_catalog`, `register_asset`, `create_project`, `get_project`, `update_project`, `validate_project`, `start_render`, `get_job`, `cancel_job`, `get_artifacts`. `create_project` и `update_project` принимают объект этой схемы. `update_project` — полная замена draft с `expected_revision`; JSON Patch в MVP не используется. Идентификатор проекта, revision, job state и пути outputs назначаются сервером и не относятся к авторскому draft.

Долгий рендер запускается через `start_render`, возвращает `job_id` и продолжается в отдельном .NET worker. Опрос идёт через `get_job`; расширение MCP Tasks не требуется для MVP. Если отсутствуют зависимости примера, результатом должны быть явные missing dependencies, а не незаявленная замена персонажа, скриншота или голоса.

## Проверка примера

Из корня пакета, с установленным Python-пакетом `jsonschema`:

```bash
python -c 'import json; from pathlib import Path; from jsonschema import Draft202012Validator; s=json.loads(Path("contracts/project.schema.json").read_text()); p=json.loads(Path("examples/novostroykin/project.json").read_text()); Draft202012Validator.check_schema(s); Draft202012Validator(s).validate(p); print("DraftProject example: schema valid")'
```

Команда проверяет структуру документа. Она не запускает TTS, не проверяет отсутствующий каталог и не выполняет рендер.
